import { Step, Prereqs, IfThisFails, Outcome } from "@/components/help/guide";

<Prereqs>
- An admin account: the email or Clerk user id must be in `Admin__Emails` / `Admin__UserIds` on the API. Your ordinary signed-in session is the admin credential — there is no separate admin token.
- The workspace whose data is being erased, and what exactly is going: the whole workspace, chosen documents, or old order records.
- A written request or ticket to point at afterwards. These actions are audited, and the audit row is only useful if you can say what it was for.
- For old order records only: `curl` or an equivalent HTTP client. Documents and whole workspaces have a button on [`/admin`](/admin); the two order erasures deliberately do not (Step 5).
</Prereqs>

<Step n={1} title="Decide whether erasure is really what is being asked for">

Four different requests get worded as "delete our data", and only the last three are this runbook:

- **"Stop keeping the files."** That is the retention window, not erasure — **Retention** on the
  workspace's row on the [admin dashboard](/admin). It removes stored source files and
  generated output on a schedule and keeps the records, the hashes, the provenance and the
  audit trail. Reversible in the sense that you can turn it off before the next sweep runs.
- **"Delete these documents."** A written deletion request for some of a workspace's documents:
  **Delete documents** (Step 3).
- **"We are leaving, and erase everything."** Cancelling the subscription already stops every
  ingest path and deletes nothing. Erasing the whole workspace afterwards is **Erase workspace**
  (Step 4).
- **"Erase this order / these orders."** An old order record, from before documents. That is
  the `curl` fallback (Step 5).

Every one of these hard-deletes the stored files **and** the database rows tied to them. There is
no soft-delete behind it and no restore path: it cannot be undone. Confirm in writing what is in
scope before you continue.

</Step>

<Step n={2} title="Find the workspace">

Open [`/admin`](/admin) and find the workspace's row in the customers table. If the request came
in quoting a PO number rather than a workspace, use the **Find an order by PO number** box at the
top of the page — it maps a PO number to the owning workspace, the order id and its status.

Note the workspace's slug, its short name: both buttons ask you to type it back before they arm.

<IfThisFails>
No matching workspace means you have the wrong one, not that it was already erased. Stop and
re-check with whoever raised the request.
</IfThisFails>

</Step>

<Step n={3} title="Delete chosen documents">

On the workspace's row, press **Delete documents**. A panel opens under the row:

1. Give the document ids, one per line (a document's id is the last part of its address in the
   app), **or** a date to delete everything received before it.
2. Type the workspace's slug to confirm. The button stays off until there is an id or a date and
   the slug matches exactly.
3. Press **Delete documents**.

The panel then says how many documents, rows and stored files were deleted. Keep that receipt with
the ticket. A document still being read or sent is left alone — run it again later. If it says
more documents match, run it again to continue.

<IfThisFails>
"Give at least one document id or a date" means the request had no filter and touched nothing.
Any other refusal may have landed part-way: run it again — documents already deleted are left out.
</IfThisFails>

</Step>

<Step n={4} title="Erase a whole workspace">

On the workspace's row, press **Erase workspace**. A panel opens under the row:

1. Type the workspace's slug to confirm.
2. If the workspace has ever paid, tick **The customer's agreement has ended** — only once it
   really has.
3. Press **Erase permanently**.

The receipt names the rows, tables and stored files erased, and the sign-in accounts removed. Keep
it with the ticket. Anything it lists as not deleted — stored files, or sign-in accounts to remove
by hand in Clerk — is yours to finish.

<IfThisFails>
The server refuses, before touching anything, a workspace that Stripe still shows a running
subscription for (cancel it in Stripe first), one billed for overage, and one with overage not yet
billed (erase it once the final invoice is out). The panel names which. Any other failure may have
landed mid-erase: run it again — if it already ran, the earlier receipt comes back.
</IfThisFails>

</Step>

<Step n={5} title="Fallback: erase old order records with curl">

Order records have no button, on purpose: the friction of typing the call is the last check
between a mis-click and a customer's records being gone. Both calls are org-scoped by their route
id — the organisation id is ANDed into every match, so neither can reach across workspaces.

Get the organisation id (each entry carries `id`, `name`, `slug`, `plan` and `accountStatus`):

```bash
curl -s "$API_BASE/api/admin/organisations" \
  -H "Authorization: Bearer $ADMIN_JWT" | python -m json.tool
```

The API authenticates the same Clerk session JWT the app itself sends; being on the admin
allowlist is what makes it an admin credential. Mint one from the signed-in app with
`await window.Clerk.session.getToken()` in the browser console, right before the call. It is
short-lived — never paste it anywhere that persists.

**One order:**

```bash
curl -X DELETE \
  "$API_BASE/api/admin/organisations/$ORG_ID/orders/$ORDER_ID" \
  -H "Authorization: Bearer $ADMIN_JWT"
```

A 200 carries per-table counts of what went — `found: true`, `r2ObjectsDeleted`, `linesDeleted`,
`artifactsDeleted`, `deliveryAttemptsDeleted` and the rest. A **404** means the order does not
belong to that organisation, or it has already been erased; the two are the same answer on purpose.

**Many orders in one batch — read the filter twice:**

```bash
curl -X POST \
  "$API_BASE/api/admin/organisations/$ORG_ID/orders/bulk-erase" \
  -H "Authorization: Bearer $ADMIN_JWT" \
  -H "Content-Type: application/json" \
  -d '{"poNumberPrefix":"E2E-API-"}'
```

The filter fields combine with **AND**: `poNumberPrefix`, `status`, `ids` (a list of order ids)
and `olderThan` (an ISO timestamp). **At least one real criterion is required** — an empty filter
is refused with **400** so it cannot mass-erase the organisation. Do not work around it with a
criterion that matches everything. A 200 carries `ordersErased` plus the same per-table counts;
`ordersErased: 0` means the filter matched nothing, a signal to re-read it rather than broaden it.

<IfThisFails>
A 401 or 403 means the token expired (mint a fresh one) or the account is not on the admin
allowlist; the gate runs before any work. A count smaller than expected means the filter is
narrower than you thought — the fields are ANDed. There is no undo, so an over-broad filter is not
something a second call can correct.
</IfThisFails>

</Step>

<Step n={6} title="Confirm the audit trail recorded it">

The two order calls write a durable audit event before they return, recording who ran it, which
organisation and entity it touched, and the result: `admin.order.erased` for one order,
`admin.orders.bulk_erased` (with the filter used) for a batch. These rows survive the erase and are
the receipt that proves it ran. If an audit row is missing, record the response body against the
ticket yourself and say so; the accountability record is a compliance obligation.

<Outcome>
What was asked for is permanently gone, and you are holding the receipt of exactly what was
removed, filed with the ticket.
</Outcome>

</Step>
